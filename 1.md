# Git Flow — рабочий процесс

## Ветки

- **main** — стабильная ветка, только релизы в продакшн.
- **dev** — интеграционная ветка для тестирования.
- **feature/xxx** — ветки для разработки отдельных фич.
- **hotfix/xxx** — ветки для срочных исправлений в продакшне.

## Правила

### main

- Запрещён прямой push (только через Pull Request).
- Требуется код-ревью (минимум 1 approval).
- Обязательные проверки CI должны проходить.
- Линейная история (Squash & Merge или Rebase & Merge).

### dev

- Запрещён прямой push (только через Pull Request).
- Можно без ревью, если команда договорилась.
- Желательны проверки CI.
- Можно мержить чаще для интеграции кода.

## Как работает код-ревью и approvals

1. **Включение**  
   В GitHub в настройках защиты ветки (`Settings → Branches → Branch protection rules`) для ветки `main` включаем:

   - **Require a pull request before merging**
   - **Require approvals** → ставим количество одобрений (обычно `1`).

2. **Процесс**

   - Автор делает Pull Request (PR) в защищённую ветку.
   - Другой разработчик с правами `Write` или выше заходит в PR и жмёт **Review changes → Approve**.
   - После того как получено нужное количество approve, кнопка **Merge** становится активной.

3. **Дополнительно**
   - Если включена опция **Dismiss stale pull request approvals when new commits are pushed**, то при добавлении новых коммитов approve снимаются, и нужно подтверждать снова.
   - Можно настроить **CODEOWNERS** — список ответственных за конкретные файлы, их approve обязателен.

## Что такое Squash & Merge и Rebase & Merge

### Squash & Merge

- Все коммиты из PR объединяются (squash) в **один коммит** в целевой ветке.
- История становится чище: один коммит = одна фича/фикc.
- Сообщение коммита обычно берётся из заголовка PR.

**Плюсы**:

- Чистая история.
- Легко откатить фичу одним коммитом.

**Минусы**:

- Исчезает подробная история мелких коммитов.

### Rebase & Merge

- Git "переписывает" историю коммитов PR так, как будто они были созданы прямо поверх последнего коммита целевой ветки.
- Сохраняются все коммиты из PR, но без merge-коммитов.

**Плюсы**:

- Линейная история без merge-коммитов.
- Сохраняются все мелкие коммиты.

**Минусы**:

- Может быть сложнее разруливать конфликты, особенно в больших командах.

**В Git Flow** обычно:

- В `dev` можно использовать **Squash & Merge** для аккуратности.
- В `main` чаще используют **Rebase & Merge** или **Squash & Merge**, чтобы история была чистой.

## Рабочий процесс

### 1. Разработка фичи

1. Отводим ветку от dev:
   ```bash
   git checkout dev
   git pull
   git checkout -b feature/имя-фичи
   ```
2. Пишем код, коммитим, пушим:
   ```bash
   git push -u origin feature/имя-фичи
   ```
3. Создаём Pull Request в dev.
4. После тестов мержим в dev (через Squash & Merge или Rebase & Merge).

### 2. Подготовка релиза

1. Когда dev стабилен:
   - Создаём PR из dev в main.
   - После merge — деплой на production.

### 3. Срочный hotfix

1. Отводим ветку от main:
   ```bash
   git checkout main
   git pull
   git checkout -b hotfix/имя-исправления
   ```
2. Исправляем баг, пушим, создаём PR в main.
3. После merge — деплой.
4. Мержим hotfix обратно в dev.
